## 当前问题

### P1：`response_peng → response_chi` 被误判为终态关闭

当前代码在统一 resolver 中只判断：

```python
if phase != confirm.phase:
    outcome = "closed"
```

这不适用于吃窗确认。对于同一个 `source_discard_seq`：

```text
expected phase = response_chi
snapshot phase = response_peng
```

它表示碰窗仍在进行、吃窗尚未到达，应为 `PENDING`，不能标记 `TERMINAL`。

本房共有 17 条：

```text
claim_miss = response_chi/window_confirm_phase_changed
```

逐条回放发现，这 17 个 WindowId 后续全部又收到了 `response_chi + authoritative_open`。其中至少 12 个同一窗口后来出现成功 chi action，其他窗口至少出现了后续的权威确认或 pass 决策。因此这 17 条不能直接解释为真实漏吃。

影响：

- `claim_miss` 被高估；
- `window_confirm_closed/miss` 被高估；
- WINDOW_CONFIRM reason 可能在吃窗真正开放前被过早清除；
- 依赖 successor 的恢复路径可能被错误地终止。

建议：

```text
expected=response_chi && actual=response_peng && WindowId 相同
    → PENDING / unconfirmed

expected=response_chi && actual 已进入 discard/timeout/下一弃牌
    → TERMINAL

expected=response_peng && actual=response_chi
    → TERMINAL
```

并增加“同一 source discard 先返回 response_peng、后返回 response_chi”的回归测试；PENDING 期间不得写 `claim_miss`。

### A01 · P1：源弃牌身份没有贯通事件、动作和重锚路径

**已确认：代码复现 + 真实日志。** 位置：[bot_client.py](../mj/platform/bot_client.py) 的 `_window_key()`（约 885 行）、snapshot carry（约 1605 行）、`tile_discarded` 分支（约 1772 行）、`_submit()`（约 2601 行）。

事件分支更新了局部 `pending_source`，却没有同步更新 `mirror._source_discard_seq`。而 `_submit()`、决策标记等路径调用 `_window_key(mirror, phase)` 时不传触发事件，只读取 Mirror 上的来源字段。该字段目前只在快照重建后的 carry 路径写入，增量新弃牌也不会清除旧值。

最小复现结果：

```text
收到 tile_discarded(seq=42)
event key source_seq = 42；action key source_seq = None

Mirror 曾 carry source_seq=42，再收到同家同牌的新弃牌 seq=50
event key source_seq = 50；action key source_seq = 42
```

因此问题不仅是 legacy 比例偏高：后者会把不同弃牌错误标成相同 authoritative 身份，可能误拦新动作，或让动作、决策、timeout 与确认的关联错位。

本房共记录 665 个 `tile_discarded`，665 个都有 event seq，0 个带显式 source 字段。15 条 legacy peng 动作之前，最近的弃牌事件全部与动作 WindowId 的 owner/tile 匹配。例如 [b1 日志](../local/games/20260911/u_9812ba08fe2f_a_4854d51057d2_r1_b1_t0.jsonl) 第 105 行已有 seq=91 的弃牌，第 107 行的动作仍是 legacy。**原报告把这批 legacy 主要解释为 snapshot-only 的说法需要收回；这 15 条已存在客户端来源传递缺口的直接证据。** 日志仍不足以证明所有其他 legacy 窗口都有同一原因。

建议：为每个 gid 维护一个规范的 current discard identity，在成功应用弃牌事件后统一替换，并在认领、换轮及失效时清理；动作、决策和确认从同一入口读取。可选择统一注入 Mirror，或向所有消费者显式传递 WindowAttemptKey，避免维护不同步的两份来源。跨 gap 重锚无法证明同窗时保留 unresolved，不以相同 owner/tile 或 snapshot watermark 猜测来源。同步传递 `identity_origin`、`first_seen_via`，三个 `_WindowConfirm` 构造分支也需覆盖。

回归建议：事件 seq=42 后立即 POST 的日志必须带 42；carry=42 后同家同牌新弃牌 seq=50 必须生成新键；旧键不能阻止新窗口，重锚后的原窗口仍应防重；覆盖 claim/换轮/缺来源的清理路径。

### A02 · P1：结构性候选证明的花色偏移计算错误

**已确认：最小复现。** 位置：[bot_client.py](../mj/platform/bot_client.py) `_structurally_no_nonpass_response()`，约 1416 行。

```python
offset, pos = divmod(tile, 9)
hand[offset + pos + left]
```

`offset` 实际是花色编号 0/1/2，并非手牌数组中的起始下标 0/9/18。因此筒、条的吃牌组合会查到别的牌位。复现使用手牌 `7b 8b 1w 1w 1w 2t 2t 2t 3t 3t 3t 东 南`、上家弃 `6b`：规则合法集存在吃（`[-2]`），该 helper 却返回 `no_nonpass=True`。

这违反了“只有结构性证明不可能有非 pass 才清 urgent”的前提。后续 `_make_chi_pending()` 在部分路径会重新建立吃需求，因此本复现证明的是错误降级条件，尚不能直接算作一次线上漏吃。

建议：用 `suit_base = (tile // 9) * 9` 或 `tile - pos` 计算花色基址；保持边界检查和未知状态的保守返回。测试覆盖万/筒/条三门、低/中/高位吃组合、1/9 边界及仅其他花色有候选的反例，不能只测试对子与单个无候选手牌。

### A03 · P1：resolver 仍混淆“身份缺失”和“身份确实改变”

**已确认：最小复现。** 位置：[bot_client.py](../mj/platform/bot_client.py) `_window_confirm_matches()` / `_resolve_window_confirm()`，约 649、707 行。

当前匹配接口只有 bool，无法区分信息不足与确定不匹配，造成两种相反错误：

- 期望 authoritative source=42，返回快照仍是同轮、同 owner/tile，但缺来源、也没有可证明的 carry：结果为 `stale`，可写 `claim_miss`。缺字段本身不能证明 WindowId 已变化。
- 期望键和快照键都为 legacy、当前 phase/deadline 合法：resolver 返回 `confirmed`，随后 reason 变为 SATISFIED、记录 `authoritative_open`。这并没有证明与原需求是同一弃牌窗口。

建议：身份匹配拆为 `MATCH / MISMATCH / UNKNOWN`。只有轮次、源序号或其他稳定身份字段明确冲突才终止旧需求；UNKNOWN 在有界等待期间保持 PENDING，不产生最终 miss。legacy 快照仍可供当前合法性判断，但“当前可行动”与“旧 authoritative demand 已满足”必须分别表达；legacy 不能进入强身份确认分母。测试应显式区分缺 source 与 source 从 42 变成 50。

### A04 · P1：持续 PENDING 缺少统一退出条件，并会重复记放弃

**已确认：fake-clock 主循环复现。** 位置：[bot_client.py](../mj/platform/bot_client.py) resolver 约 739–787 行、snapshot 后处理约 1640–1687 行、`_act_on_snapshot()`。

新 deadline 检查只位于“expected chi、actual peng”的分支。actual 已是 chi 但一直缺少精确 deadline 时，即使 `schedule_deadline` 已过，仍返回 `unconfirmed/PENDING`。主循环保留 reason 后又调用 `_act_on_snapshot()`，后者针对缺 deadline 反复执行 `_state_abandon()`。

复现：等待截止=102、当前 monotonic=102，连续四份同窗 chi 快照均缺精确 deadline。四次结果都是 `unconfirmed`，并产生 `client_state_abandons=4`、`auto_played=4`；这些只是四次观察同一问题，并无四次服务端代打证据。

另外，同窗旧 peng 快照从 snapshot 分支生成 successor 时，不经过事件侧 `EAGER_CHI_GAP/EAGER_CHI_MAX` 的完整计数与间隔控制。固定快照延迟 100ms 的复现中，进入 chi 等待后可连续确认 9 次；这些路径没有共享一份统一的确认预算。反复重建 wait-state 还会重新换算 deadline，浮点微差可能被视为 metadata 变化。

建议：将窗口整体等待期限、重试次数和最早下次抓取时间保存在同一份确认需求中；所有 PENDING 出口执行同一有界等待规则。等待预算耗尽时终止/降级确认需求并记录具体原因，缺少服务端终态证据时不能宣称发生了真实漏窗。PENDING 的旧快照不得触发最终 abandon/miss；放弃统计按 `(WindowId, phase)` 去重，缺字段记录与服务端代打分开。重新观察同窗不得无意重置预算。

回归建议：同窗 peng→peng→chi 的主循环中，第一次 PENDING 后 reason 仍存在、`_claim_miss` 未调用；缺 deadline 到整体等待期结束应停止 FULL 连抓；多次旧快照不能重复增加最终放弃数；新弃牌/新轮与反向 peng→chi 仍应 TERMINAL。

### A05 · P2：successor 在 reason-specific completion 完成前被统计

**已确认：按生产调用顺序复现。** 位置：[bot_client.py](../mj/platform/bot_client.py) 约 1545、1599 行，以及 [state_demand.py](../mj/platform/state_demand.py) `reconcile()` 约 457–509 行。

主循环先 `demand.reconcile()`，之后才成功应用快照、`finish_resync()` 和运行窗口 resolver。前一步看到 RESYNC/WINDOW_CONFIRM 尚为 PENDING，已增加 `logical_demands` 与 `successor_requests`；后一步可能立即满足它们，实际上无需 successor。

```text
submit_resync → start_request → 返回有效 snapshot
reconcile → finish_resync
has_pending=False，start_request()=None，但 successor_requests=1
```

建议：先收集快照应用与各 reason 的结果，再执行一次完整 reconciliation；或者将“后继需求候选”和“实际创建 successor”分离，只在确实创建后继时计数。终局 completion 也不得产生不存在的 successor。保持每 gid 单在途，不需要增加并行请求。

回归建议：RESYNC 一次成功、WINDOW_CONFIRM 一次 confirmed 均 successor=0；旧 phase/未覆盖 watermark 只有实际继续请求时才加 1。首房恢复出的 successor=50 目前属于原始计数，不能直接解释为 50 次必要后继。

### A06 · P2：recorder 的 req_fallback 来源被 acceptance 再次升级

### A07 · P1（验收）：完整性被简化为“有 end”，受影响层仍可能进入主汇总

### A10 · P1（验收）：新 gap 分类会把无法证明的缺口归成正常追赶

**已确认：最小输入复现。** 位置：[window_acceptance.py](../scripts/window_acceptance.py) `_gap_record()`，约 43–108 行。

当前分类存在三处过强推断：

- 只要响应有 snapshot 就归为 `snapshot_reanchor`，且直接 `decision_impact=false`；这描述的是响应形式，不能证明缺口原因，也没有检查 Mirror 是否成功应用快照。snapshot/req 日志均先于成功重建确认落盘。
- requested=12、响应 seq=15、事件只含 seq=15 且 `gap=true`，随后有 decision，被归为 `sse_batch_catchup`、strong_risk=0。代码没有证明 13/14 是否可见、是否应连续；明确连续性失败应列为 event_discontinuity，协议可见性不明则列 unknown，不能自动认定为正常合批。
- 向后找 events 没在下一条 req 截止，会借用下一次响应的 events；decision_impact 扫描又在 reset 处提前结束，而 reset 不等于已成功重建。

**修正上一轮结论：** 首房的 51 条确实被当前新脚本全部输出 `snapshot_reanchor/decision_impact=false`，但这是上述规则的结果，不能据此声称 51 条均已证明没有风险。本轮额外对照快照轮次：17 条发生可见 round_no 变化，34 条同轮或无法由轮次变化解释，仍应保留各自的上下文。即便快照前没有错误决策，缺口覆盖期间也可能错过一个窗口；“决策未使用缺口状态”不等于“窗口机会无损”。

建议：以一次请求的响应边界关联 req→snapshot/events；分别记录 `gap_cause`、`recovery_status`、`decision_impact` 和可判定性。通过同轮/换轮、预期与实际可见序列、retry 链判断原因，证据不足用 unknown；通过成功重建证据判断恢复。修改当前把“12→只收到15”预期为正常追赶的测试，补连续批次、真缺口、retry 同时有缺口、snapshot 应用失败、日志截断和下一次 req 不串联等场景。

### A11 · P2：queue 只取最后一次许可，16.2 秒长尾主要是退避

**已确认：原始 attempt 明细。** 位置：[bot_client.py](../mj/platform/bot_client.py) `_throttle_ticket()` 约 2111 行、[window_acceptance.py](../scripts/window_acceptance.py) `request_group()` 约 279 行。

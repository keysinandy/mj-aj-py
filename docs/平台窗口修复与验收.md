# 平台窗口修复与验收（2026-09-10）

## 范围与依据

本次针对 `python3 -m mj.platform.match_runner --games 10` 的窗口响应、
动作提交与恢复路径，不改麻将引擎、模型权重或策略选择。

规则依据：仓库保存的《杭州麻将对战平台》接入指南，以及本次只读查询的
线上指南 v29。碰窗、吃窗默认各 1 秒且顺序固定；弃牌窗默认 3 秒；
收到 409 后需以 `seq=0` 重建；快照是对应 seq 的规范状态；响应窗口
成员不等于“尚未响应成员”，客户端必须防止重复提交。

v28、v29 的新增变更未修改上述时序协议。`window_deadline_ms` 是当前
阶段的绝对毫秒截止，不能将碰窗截止误作吃窗截止。不同机器的时钟偏差
与网络尾延迟仍会影响推算，不能用事件 ts 单独证明真实开窗/接受时刻。

## 已确认的问题

- 同批上家弃牌和本人碰窗超时会取消整个响应触发，连带丢失吃窗。
- 吃牌等待目标按观察时刻再加一整秒，可能推过吃窗关闭点；睡醒与
  模型决策完成后缺少最终截止检查。
- 409 被记录后直接返回，未执行文档宣称的快照恢复。
- 碰窗快照产生的吃窗等待态被丢弃，旧等待态又可能跨快照残留。
- 吃窗等待依赖下一次长轮询返回，网络等待可能吞掉动作机会。
- 动作 POST 复用通用重试，在响应丢失时可能重复执行旧动作。
- CLI 的 SSE 对照开关未实际开启 SSE。
- 日志将响应完成时间当作动作提交时间，无法可靠区分发送晚和响应慢。

## 验证门槛

1. 用假时钟、明确 phase 和截止时间的假服务器验证原失败用例；
   不能以“完全不提交”换取零 409。尚有窗口预算时应保留合法吃牌机会。
2. 检查碰超时转吃、吃超时取消、他家优先认领、跨局/gap、409 重锚、
   响应丢失、成功回声防重和十场隔离。
3. 回归 API、镜像、记录器、完整本地对局以及既有测试。
4. 离线通过后运行默认参数 10 场，整房收官；期间不并跑重负载测试。
5. 分别报告动作成功/拒绝、客户端截止放弃、POST 结果不确定、本人
   服务端 timeout 事件；无合法选项的代过、策略主动过与丢失机会分别看待。

线上观测无法保证捕获所有机会：gap/主动快照可能覆盖未收到的事件。
缺失数据必须说明，不把“未记录到”写成“没有发生”。一次 10 场也不
足以证明任何网络条件下零漏窗。

## 吃/碰/杠 机会损失日志(`claim_miss`)

对局 JSONL 新增 `claim_miss` 记录，专门回答一个问题：**规则允许吃/碰/杠，
但这一次没有成功——是策略没做，还是做了没成？**

写入条件（`BotClient._claim_miss`）：phase ∈ {`response_peng`,
`response_chi`}，镜像当前能算出至少一个非 `pass` 合法动作，且满足以下
两类之一。其余情况一律不写（无合法动作自动过、**策略明确 `pass`**、镜像
张数漂移无法评估）。

客户端按窗口身份（`_window_key`）记录本窗已完成的本地决策
（`_window_decisions`），timeout 归因据此三分类：

| 类别 | `chosen` | `client_decision` | 含义 |
|---|---|---|---|
| 策略已选动作但未成 | 具体动作 | `true` | 客户端确实决定吃/碰/杠，请求被拒、结果未知或本地放弃提交 |
| 未决策即被 timeout | `null` | `false` | 服务端 timeout 时规则仍有合法动作，但策略尚未完成决策 |
| 已决策为 `pass` | — | — | 本窗已本地决定过牌 → **不写记录**（碰窗也不计代打） |

`reason` 取值与来源：

| reason | 类别 | 触发点 |
|---|---|---|
| `server_timeout_peng` / `server_timeout_chi` | 未决策 | 服务端 response timeout 事件到达 |
| `decision_boundary_resync` | 已决策 | 决策耗时后接近碰窗边界，重锚确认 |
| `window_already_attempted` | 已决策 | 同一窗口身份已尝试过，抑制重复提交 |
| `action_rejected` | 已决策 | POST 返回明确拒绝（含 409） |
| `action_uncertain` | 已决策 | POST 超时/响应丢失，结果未知 |
| `碰窗精确截止已到` | 已决策 | 提交前精确截止已过 |
| `吃窗截止前已无提交余量` / `吃窗在等待后已关闭` | 已决策 | 吃窗等待前后复查截止失败 |

字段：

```json
{"type": "claim_miss", "phase": "response_chi", "reason": "action_rejected",
 "legal": [-4, -1], "chosen": -4, "client_decision": true,
 "chosen_legal": true, "legal_check": "current_mirror",
 "payload": {"action": "chi", "tile": "2b"}, "status": 409,
 "code": "INVALID_ACTION", "pending": [2, 13], "seq": 399,
 "deadline_at": 1789028256.912, "decision": 42}
```

- `legal` 为当时镜像 `legal_actions()` 的非 `pass` 子集；`chosen_legal`
  与 `legal_check` 标记所选动作是否落在该集合内（`not_decided` 表示
  策略未决策、`stale_or_mismatched` 表示集合与选择不一致，需人工复核）。
- `decision` 复用 `decision` 记录的 id 配对；若动作实际发出过 POST，同一
  `decision` id 还会出现在 `action` 记录里（`ok=false`），两条记录互补：
  `action` 看传输结果，`claim_miss` 看“本来能做却没成”。
- `pending` 为 `(出牌者, 牌值)`；`seq` 为写下该记录时的事件游标。

口径边界：`claim_miss` 表示“规则上有机会且未成功”，**不等于策略本来
一定会执行该动作**。统计漏窗损耗时应按 `reason` 分开看：只有
`client_decision=true` 的部分才是策略已决定却未落地；`server_timeout_*`
配合 `chosen=null` 的部分是决策预算不足的证据（策略主动过已在上游
过滤，不会出现在日志里）。

## 线上验证（2026-09-10，默认 12.5/s）

房 `a_59753d3945aa`，`--games 10`，10/10 局完成：

```text
actions=865 失败=0 err409=0 post_uncertain=0
client_deadline_abandons=0 auto_played=1 mirror_resets=0
my_timeout_peng=2084 my_timeout_chi=636
claim_miss=25（response_chi/server_timeout_chi 23、
              response_peng/server_timeout_peng 1、
              response_peng/decision_boundary_resync 1）
```

日志目录 `local/games/20260910/u_9812ba08fe2f_a_59753d3945aa_r1_b*.jsonl`。
对 23 条 `server_timeout_chi` 逐条按其 `pending` 回放配对本地决策，结果
全部为“该窗口从无本地决策”（不是策略过牌被误记），说明 `chosen=null`
的 `not_decided` 标注在本轮准确。本轮之后补入了 `_window_decisions`
跟踪（上面第三类），把“已决策为过”从统计中剔除。

### 修补后第二轮（房 `a_8bbc394d729b`，10/10 局）

```text
actions=925 失败=0 err409=0 post_uncertain=0
client_deadline_abandons=0 auto_played=0 mirror_resets=0
my_timeout_peng=2238 my_timeout_chi=683
claim_miss=41（全部 response_chi/server_timeout_chi/chosen=null）
本地 chi 决策 65 次，动作分布 chi=65 全部提交成功
```

对 41 条 `claim_miss` 独立回放归因（不依赖 `_window_key`，直接用
`pending` 配对）：**41/41 为「该窗口确无本地决策」**；本轮没有任何
“已决策为过”被写入。口径上：吃窗可吃共 106 个窗口，客户端在 65 个
窗口内完成决策并提交成功，41 个窗口未及决策即被服务端 timeout。

推论（待进一步验证）：吃窗决策的瓶颈是**在 T+2 之前拿到权威
`response_chi` 快照**——拿到快照的窗口 65/65 都成功，没拿到的 41 个
全部丢失。这与 `/state` 排队 p95 同量级（本轮 max 1270 ms），指向
调度优化而非策略问题。

### 未及决策的根因（基于 `a_8bbc394d729b` 逐窗口回放）

**不是模型慢**：成功窗口里 `decide` 耗时 p50 = 5 ms、max = 26 ms。

**成功路径**（65 个窗口）：权威 `response_chi` 快照在 T+1.1~T+1.7 到达
（p50 = T+1.52，T = 弃牌事件 ts、秒级），随后 POST 在 0.02~0.18 s 内
完成 → 稳落在 T+2 之前。

**失败路径**（41 个窗口）：快照在 T+2 前从未到达。逐窗口统计：
41/41 窗口内**没有任何快照响应、也没有 `seq=0` 请求**，窗口内只有
2~3 次普通增量轮询，单次端到端 ≈ 1.0 s。以
`b0_t0` seq=110 为例（T=904）：

```text
903.917 观测到弃牌 8w（请求排队 753ms，已迟到 0.9s）
904.151 取得 pass(0)              ← 第 1 次请求返回
904.928 取得 peng timeout(2,3)    ← 第 2 次请求返回
905.919 取得 chi timeout(me, ts=906=T+2) ← 第 3 次请求排队~1s 后返回
```

即第 3 次请求在 T+1 前后发出、本应带回 `response_chi` 快照，实际被排队
拖到窗口关闭之后才返回，批内直接是吃窗 timeout。

**两层成因**：

1. **往返成本 ≈ 窗口宽度**（主因）：该房 `/state` 端到端 p50 = 819 ms
   （排队 p50 739 ms + 服务端 hold p50 29 ms，hold ≥900 ms 占 3.8%）。
   10 场共享 12.5/s 使队列饱和，客户端请求节奏 ≈ 1 次/秒；而吃窗只有
   1 秒宽（T+1~T+2）且权威快照只能在 T+1 之后才有意义——等于用 1 秒
   粒度的采样去命中 1 秒宽的窗口，命中率 ≈ 65/106 = 61%。
2. **等待逻辑放大器**：`_make_chi_pending` 的 `needed` 含自己
   （`{me} ∪ 其他未冻结座位`），而 `seen` 只在收到 `pass` 或**他家**
   timeout 时增长；自己若无碰牌选项就不会提交 pass、自己的 timeout 又
   走 `mine` 分支不计入 `seen`，于是 `seen < needed` 恒真，客户端必然
   等到 `ready_mono`（T+1）才去请求权威吃窗快照，把"必须落在 T+1 之后
   的一次往返"变成硬路径。

**我方 timeout 事件的口径归因**（同房，逐条回放合法集）：

```text
my_timeout_chi  = 683  →  642 无合法吃牌（无事可做，零损失）
                          41 有合法吃牌（即上表的漏吃）
my_timeout_peng = 2238 → 2238 全部无合法碰/杠（零损失）
```

即 `my_timeout_*` 是**服务端窗口关闭事件计数**，绝大多数没有任何可执行
动作；只有与 `claim_miss` 交集的那部分才是真实损失。

**修复方向**（按性价比排序，均未实施）：

1. 降低往返成本：把共享排队 p50 从 739 ms 压下去（提高 `--state-rate`、
   多令牌分摊、按场次隔离配额）。
2. 削减非窗口请求占用：普通轮询占满了共享配额，窗口请求虽有 EDF 优先
   但队列已饱和；SSE 帧合并/每场单在途请求可腾出余量。
3. 修正 `seen` 语义：无碰牌选项时把自己视为已响应，使客户端在 T+1
   一到就能立即发起快照请求，而不是等 `ready_mono` 到期。
4. 兜底（有风险）：T+1 前用已知 pending + 合法集预决策，快照到达后仅做
   校验再 POST——保留"确认后才提交"以维持 0 个 409。

统计命令：

```bash
python3 -m mj.logview <gid>            # 时间线里显示 MISS 行 + 摘要分类计数
python3 -m mj.logview <gid> --types claim_miss,action,decision

python3 - <<'PY'
import glob, json
from collections import Counter
c = Counter()
for path in glob.glob("local/games/**/*.jsonl", recursive=True):
    for line in open(path, encoding="utf-8"):
        r = json.loads(line)
        if r.get("type") == "claim_miss":
            c[(r["phase"], r["reason"], r["client_decision"])] += 1
for k, n in c.most_common():
    print(n, k)
PY
```

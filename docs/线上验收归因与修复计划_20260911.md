## 4. 已确认客户端根因与潜在风险

### R1 · P1：确认、决策和动作三个生命周期未闭合

位置：`mj/platform/bot_client.py` 的 `_resolve_window_confirm()`（755）、快照主循环（1754）、`_make_chi_pending()`（1120）、`_act_chi()`（2717）。

resolver 返回 PENDING 后，主循环保留 `window_confirm`，但仍调用 `_act_on_snapshot()`；chi 分支可以成功提交或选择 PASS。之后没有按动作/决策结果关闭旧确认。下一次快照进入 draw，resolver 又仅用旧的 `confirm.legal` 和 `confirm.chosen` 记 miss；chi 的 chosen 没同步真实 decision，因此仍可能是 None。

直接证据链：**b8:373 unconfirmed → :376 chi 200 → :377 旧 WINDOW_CONFIRM 再发 FULL → :379 stale → :380 claim_miss**。该请求入 throttle 时使用的是已经过去的估算 deadline，正是报告唯一的 deadline_missed。

PASS 也没有一致的终止检查：`_act_chi()` 记录 -1 后返回，但 `_make_chi_pending()` 只看 attempted，不看已决定 PASS。b2/377 连续决策 4 次、b4 的同一快照窗口决策 8 次、b9/204 决策 3 次，均为 PASS。仅这三处就有 12 次多余决策。

修复要求：

- 保留 StateDemand 现有三态；另用统一窗口阶段结果关联 confirmation、decision、action，不能用三份互不知情的状态判定完成。
- 当前有效快照授权成功即完成相应确认；动作成功/策略 PASS 后不得再为同一窗口阶段创建确认 successor，不得改记 miss。选择 peng PASS 只结束本家的 peng 响应，不能同时抹掉后续 chi 候选。
- 409/未知 POST 保留 attempted 防重并转 RESYNC；已选动作与响应结果必须关联同一 WindowAttemptKey。
- 对手优先级、新窗口/新局、客户端确认预算耗尽分别记录终止原因；只有满足明确损失定义的情况进入 claim_miss。
- 不要简单改成“所有 PENDING 都禁止动作”：旧窗口身份 UNKNOWN 与当前快照可证明的本家合法性是不同维度。legacy 当前快照可按安全规则决策，但不能因此把未知旧身份伪记为 SATISFIED，也不能反复复活旧确认。

### R2 · P1：粗时间越权，重试预算/截止随等待态重建失去一致性

位置：`_resolve_window_confirm()` 842 附近、`_window_confirm_retry_expired()` 744、快照分支 1800 附近。

当前在身份匹配后仍执行 `exact > source_ts + 2*WINDOW_SEC → identity_unconfirmed`。整数秒事件 ts 不是精确弃牌时刻，不能否定同窗精确 deadline。b8/330 的事件 ts=1789122259，而权威 chi deadline=1789122261.508，差出的 508ms 被错误当作身份问题。

本房记录 17 次 `deadline_outside_source_window` unconfirmed，另有 4 次 `confirmation_retry_exhausted`。后者不能直接理解成重试了 8 次：实现也会在估算 retry_deadline 到期时返回该原因。b2/b6 的有效 chi 快照先被记 expired，随后同一主循环却仍发 chi，暴露确认与动作判断矛盾。

旧 peng 快照返回 PENDING 后，主循环又从 chi 等待态新建 `_WindowConfirm`，可能重置 pending_retries/预算。当前所谓“共享有界预算”尚未贯穿整个逻辑窗口生命周期。

修复要求：

- `estimated_ready/deadline` 只作调度提示；身份由身份链决定；当前 phase 的 `exact_deadline` 决定动作授权与截止。不能把估算截止误称为服务端关窗。
- 新精确快照到来时同步更新 demand 的有效调度截止；不能继续沿用更早的事件估算。peng 精确截止只能预测 chi ready，不能冒充 chi 精确截止。
- 每个逻辑 WindowId/phase 使用持续的 client confirmation budget，同快照/旧 phase 重建不重置；一条 completion 只消耗一次预算。区分 attempt-limit 与 budget-deadline 的终止原因。
- 发送/重试前重新 reconcile 已完成或过期的窗口 reason；剩余 SSE/RESYNC 可作为普通 catch-up 继续，但不能带着旧 urgent 优先级和旧截止运行。

### R3 · P1：普通 peng 路径缺少统一授权，PASS 丢失 deadline

位置：`_act_window()` 2616，尤其普通事件快速路径与末尾 `_submit(...,-1,"response_peng")`。

catch_play 和接近秒级估算边界会确认，但其余普通事件仍可仅凭 Mirror 构造 peng 合法集并发 POST；无精确 deadline 时 timeout 落到 35s。即便来自权威快照，PASS 分支也没有传递该 deadline。

建议：有结构性非 pass 候选的响应，统一检查当前权威 phase、本家 responding seat、精确有效 deadline 和动作防重；非 pass 与显式 PASS 共用最终 deadline 检查/传递。事件若不含这些授权字段，则合并一个 urgent FULL；不得因 local phase stale/catch_play freeze 未知清 urgent。

取舍：统一快照授权会增加普通 peng 候选的确认成本，但补上了可测试的安全边界。仅补 PASS deadline 与临界重检改动较小，却保留无权威 phase 的拒绝风险；若采用分阶段提交，应明确它只是部分修复。不要给每张无候选弃牌都添加 FULL，也不要提高 rate 来抵消成本。

### R4 · P1 安全审查：carried identity 的证据不能循环自证（潜在风险）

位置：快照重建 1722 附近。没有显式 source 字段时，仅在旧 `pending_source` 的 round/owner/tile 与新 Mirror 相同就 carry event seq，随后 resolver 以该 carried seq 判断 MATCH。

如果未消费事件期间同局同家再次打出同牌，三元组相同不证明源弃牌相同；把旧 seq 注入新 Mirror 再比较会循环自证。本房未证实发生此类误绑定，不能计作某个 409 的已知根因。

因此 R2 不能孤立地删除粗时间分支后宣称身份安全。需要同时审查 carry 的事件连续性与失效条件：有显式 source 优先使用；连续已消费事件能证明同窗才 carry；跨未覆盖 gap/reanchor 且无法排除新弃牌时保留 UNKNOWN。snapshot watermark 可用于覆盖/新鲜度检查，不能冒充 source identity。服务端提供稳定 `source_discard_seq` / opaque window ID 是彻底解决 snapshot-only 身份缺口的途径。

## 5. 429、gap 与 legacy 的归因

### 5.1 429 有窗口影响，但限流来源还未定位

137 次中 SSE_DELTA=133、WINDOW_CHI=4，全部最终重试到 200。4 个 urgent 链如下：

| 请求位置 / source | 总耗时 | 实际链 | 后果 |
| --- | ---: | --- | --- |
| b3:422 / 362 | 1281.8ms | 429 HTTP268.0 → backoff500 → queue64.3 → 200 HTTP442.9 | 下一快照已 draw，未形成 chi 决策 |
| b7:312 / 269 | 1082.0ms | 429 → backoff500 → 200 | 最终策略 PASS；后续 miss 属误报 |
| b7:370 / 316 | 928.9ms | 429 → backoff500 → 200 | 拿到有效 chi，随后发生正余量 409 |
| b9:1673 / 1372 | 1047.6ms | 429 HTTP259.2 → backoff500 → queue57.6 → 200 HTTP223.2 | 下一快照已 draw，未形成 chi 决策 |

因此 2 个未提交 chi 候选均受 429 重试链影响；不能说只是 pre-read 慢，也不能证明去掉 backoff 就一定能吃到。137 个 429 的发生原因仍需服务端限流桶/请求到达证据；本房不支持“重试绕过 limiter”这一旧根因。

先补完整链的 request_kind/pending reasons、状态序列、Retry-After 原值、各次 queue/HTTP、backoff、截止来源与剩余量、最终权威快照时刻。HTTP pre-read 包含连接/TLS/网络/服务端等待等未分解部分，不直接命名为服务端耗时。跨服务端日志的关联键应为 room+gid+logical_request_id+attempt_index。

后续若确需改 retry，另开有明确验收的变更，测试超长 Retry-After、HTTP-date、deadline 过期和剩余普通需求。不要把减小 sleep、调低/调高 rate 与窗口修复放在同一个线上实验。

### 5.2 legacy 是两段观察生命周期，不是 20 个丢失窗口

本房 2658 条已记录 tile_discarded 都有 event seq，显式 `source_discard_seq/last_discard_seq/discard_seq` 覆盖为 0；445 个 snapshot 的上述显式字段也为 0。已记录弃牌事件可以提供 source identity，但 snapshot-only 窗口仍存在协议缺口。

20 条 legacy 记录实际分布：

### 8.2 P1：11 次窗口服务端超时，当前只能定位到“窗口未在截止前完成动作”

**现象。** 日志记录了 8 次 `response_peng/server_timeout_peng` 和 3 次 `response_chi/server_timeout_chi`。这些记录都带有非空合法集（peng 为 `[-5]`，chi 为 `[-2]` 或 `[-3/-4]`），但没有对应的成功动作 POST；运行日志显示本家窗口交给服务端代打。

**已确认原因边界。** 这不是旧动作自动重发造成的，也不是 StateThrottle 报出的 deadline miss；本房 `state.deadline_missed=0`，且没有 `post_uncertain`。更准确的当前结论是：客户端在可观测日志中没有完成这些窗口的动作提交，可能涉及确认快照到达过晚、HTTP/429 长尾、决策路径未选择动作或服务端窗口竞争。现有 `claim_miss` 没有保存对应 WindowId、精确 deadline、logical request 和 deadline 剩余量，因此不能把 11 次全部归因到某一个环节。

**解决方案。**

- 给每条 `claim_miss` 增加 `window_id/window_attempt_key`、`logical_request_id`、`confirm_seq`、`exact_deadline_at`、`observed_at`、`deadline_left_ms`、`legal`、`chosen_action` 和 `action_posted`。
- 将结果拆成 `deadline_expired_before_confirm`、`deadline_expired_before_decision`、`deadline_expired_before_post`、`server_timeout_after_post`、`action_rejected`、`opponent_preempted`；不能继续用一个 `server_timeout_*` 覆盖整个链路。
- 用同一份窗口证据关联 `window_confirm → decision → action → terminal snapshot`，下一房先验证是哪一段耗时，暂不通过调低 rate、修改 sleep 或改变策略来掩盖问题。
- 如果确认是 urgent 快照被普通 SSE 长尾挤压，再单独设计 urgent 预算/限流实验；该实验必须保持当前 15/s 对照组。

### 8.3 P1：4 次 409，包含普通动作失步和一次窗口动作竞态

**现象。** 4 次均为 `INVALID_ACTION`：两次普通 discard 的 HTTP 耗时约 2.742 秒，一次 draw/hu 耗时约 77ms，一次 response_peng/peng 在发送时剩余约 169ms、响应时剩余约 83ms。4 次之后都立即创建 seq=0 RESYNC，未重发原动作。

**原因判断。** 普通动作 409 表现为本地决策到服务端处理期间状态已推进的 stale-action 竞态；其中两次长 HTTP 使动作更容易落后，但无法仅凭客户端 pre-read 定位为网关、服务端还是网络等待。窗口 peng 已拿到 `authoritative_open`，仍被 409，说明存在服务端处理时刻与客户端确认快照之间的并发竞争；不能把它算成客户端重复 POST，也不能仅凭响应完成时间断言服务端在截止后才收到。

**解决方案。**

- 保持当前安全边界：409/未知 POST 只标记 attempted，立即 seq=0 重锚，禁止重发旧动作。
- 在 action 日志中补充发送前/响应后的 `phase`、`responding_seats`、`window_id`、精确 deadline、剩余时间和服务端 trace id；普通动作也记录决策所依据的 snapshot seq。
- 对窗口动作增加“权威快照距 deadline 的最小安全余量”检查；余量不足时放弃 POST 并记录 `client_deadline_abandons`，不要把必然竞态变成 409。该阈值需要离线回放和对照房确定，不能直接调大。
- 向服务端索取同一 gid/window 的动作到达时间、处理 phase、关窗原因和 trace id，专门核对本房的 1 次 window action 409。

### 8.4 P1：2 个逻辑窗口仍是 `legacy_unresolved`

**现象。** 原始 JSONL 中有 14 条 legacy 记录，实际集中在 2 个逻辑窗口（一个 `response_peng`、一个 `response_chi`），不是 14 个独立窗口。其余窗口记录使用 `tile_discard_event_seq` 或连续重锚后的 `carried_event_seq`。报告没有把 legacy 窗口纳入 authoritative 强证据分母，且 `legacy_boundary_misses_later_succeeded=0`。

**原因。** 这些窗口只能从 snapshot 首次看到弃牌，快照没有稳定的 `source_discard_seq`，客户端不能证明该快照对应哪一次弃牌。snapshot watermark、牌河长度、同家同牌和普通 `seq` 都不能替代 source identity。当前证据不足以判断是服务端未发送弃牌事件，还是事件没有被客户端记录。

**解决方案。**

- 短期继续保留 `identity_origin`/`first_seen_via`，legacy 只参与诊断和当前快照合法性判断，不进入 authoritative completeness 强分母。
- 在线日志增加“首次见于 event/snapshot/reanchor”和显式 source 字段覆盖统计，按窗口而不是按重复 confirm 行计数。
- 长期要求协议在弃牌事件或权威窗口快照中稳定提供 `source_discard_seq` 或 opaque `response_window_id`；不要在客户端新增猜测 fallback。

### 8.5 P1/P2：149 次 429 主要发生在普通增量链，尚不能归因于 rate 配置

**现象。** 149 次 429 最终都重试为 200；其中 SSE_DELTA=145、WINDOW_CHI=4、WINDOW_PENG=0、RESYNC=0。普通 state p95 latency=1130.4ms，urgent p95=231.6ms；没有 deadline miss，也没有 502。

**解决方案。**

- 保持 15/s、sleep、retry 策略和 BOT 不变，继续收集至少 2–4 个同配置房间作为对照。
- 每条物理尝试保留 `request_kind/reason_mask/logical_request_id/attempt_index/status/retry_after/queue_ms/http_ms/backoff_ms/deadline_left`，并按 logical request 重建完整链。
- 若服务端确认是配额桶问题，再单独开 rate/retry 变更；不要与窗口状态机修复混合上线。

### 8.6 P2：gap 目前没有显示决策影响，但仍需防止“无影响”被误读成“无丢失”

本房 71 次 gap 全部被分类为 snapshot reanchor 或 transport retry，decision impact 均为 false，没有 `event_discontinuity` 强风险。该结果只说明已记录决策没有落在 gap 影响链上，不能证明 gap 期间不存在未记录窗口。

### 8.7 P2：game 层是协议证据缺口，不应通过客户端伪造 complete

解决方案是：transport/window 继续按各自完整性统计；game 层保留 partial，直到服务端提供 `round_ended` 或等价 settlement marker。若业务接受协议跳过，则明确记录 `protocol_skipped`，不能把 10 个 gid 当成 game-complete 样本。

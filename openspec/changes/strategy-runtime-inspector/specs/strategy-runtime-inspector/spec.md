# Spec Delta

## Purpose

The Strategy Runtime Inspector lets operators inspect the effective strategy configuration and the execution path that produced a recorded action. It provides the same evidence in session status, replay, and command-line diagnostics without changing policy decisions.

## ADDED Requirements

### Requirement: Effective strategy configuration is published as a shared snapshot

The system SHALL publish a versioned Strategy Snapshot derived from the resolved runtime strategy and its effective profile. The snapshot MUST identify strategy, evaluator, profile, configured feature states, applicable budget/frontier values, and a stable configuration hash. It MUST distinguish disabled, unsupported/not applicable, and unknown values, and MUST NOT include credentials, opponent concealed hands, or wall order.

#### Scenario: Default legacyV2 snapshot
- **WHEN** a session loads the default online legacyV2 profile
- **THEN** the snapshot reports weighted two-ply, Stage B, and shape guard as configured on, frontier limit 3, soft/hard budgets 40/50 ms, and BigHandIntent and plus_one as off
- **AND** the hash is derived from the effective public configuration

#### Scenario: Unsupported evaluator features
- **WHEN** a policy or random strategy does not expose a LegacyV2 feature
- **THEN** the snapshot reports that feature as not applicable or unknown instead of claiming it is disabled

#### Scenario: Snapshot security
- **WHEN** a snapshot is stored in session progress, game metadata, or replay
- **THEN** it contains no bearer token, opponent concealed state, or true wall order

### Requirement: Runtime decision audit records the actual execution path

Each recorded strategy decision SHALL include a bounded Decision Audit with a normalized `decision_scope` (`baotou_scope`, `weighted_two_ply`, `legacy`, `reaction_v2`, `kong_continuation`, `fallback`, `policy`, `policy-v3`, `random`, or `unknown`), result action, elapsed time, and feature states for configured, eligible, entered, and completed where applicable. Weighted two-ply and Stage A/Stage B MUST be represented separately. Audit fields MUST come from the actual evaluation result and MUST NOT infer execution from the selected evaluator name alone.

#### Scenario: Specialized early return
- **WHEN** a legacyV2 discard returns through `baotou_scope`
- **THEN** the audit reports `decision_scope=baotou_scope`, weighted two-ply configured but not entered, and the explicit early-return reason

#### Scenario: Weighted search completes with Stage B
- **WHEN** a legacyV2 decision completes weighted search after entering Stage B
- **THEN** the audit reports the search as entered and completed, Stage B as entered, and the actual selected action

#### Scenario: Budget fallback
- **WHEN** the weighted search is entered but cannot produce an accepted result before its budget
- **THEN** the audit records the timeout or fallback reason and does not claim that weighted search selected the action

#### Scenario: Stage B is enabled but skipped
- **WHEN** Stage A safely proves a winner before Stage B is needed
- **THEN** Stage B is shown as configured but not entered with a skip reason, while the overall audit preserves the actual decision scope

### Requirement: Web session pages show configuration and load state

The console and tournament pages SHALL display the session's effective Strategy Snapshot alongside strategy load state. A page MUST distinguish configured/loading/loaded/error states and MUST NOT label an unstarted or old session as loaded based only on the currently selected form value.

#### Scenario: Console session is running
- **WHEN** a local arena or online match session has published its runtime snapshot
- **THEN** the console shows the resolved evaluator/profile, active feature switches, and configuration hash for that session

#### Scenario: Tournament strategy is loading
- **WHEN** a tournament session is still loading its strategy
- **THEN** the page shows loading state and the requested strategy, then displays the resolved snapshot after construction succeeds

#### Scenario: Strategy construction fails
- **WHEN** strategy loading fails
- **THEN** the page shows an error state and does not display a loaded snapshot

### Requirement: Strategy selectors preview the resolved configuration
The console and tournament strategy selectors SHALL show a preview generated by the shared backend Strategy Snapshot builder for the current selection. The preview MUST be labeled as configured and MUST NOT claim the strategy or model has loaded. It MUST refresh when the selection changes and show the applicable feature switches, profile values, and configuration hash.

#### Scenario: Online match strategy selection
- **WHEN** an operator selects a strategy under “线上匹配 · 我的策略”
- **THEN** the UI shows the backend-resolved evaluator and enabled features before the session starts
- **AND** the preview identifies itself as the current selection, with the loaded session snapshot remaining the runtime confirmation

#### Scenario: Model strategy has no selected model
- **WHEN** an operator selects a model-backed strategy but has no available selected model
- **THEN** the preview shows the strategy configuration and a clear model requirement warning

### Requirement: Replay exposes the audit attached to the selected decision

The replay backend SHALL preserve a decision's Strategy Snapshot and Decision Audit on the matching replay metadata/step. The replay UI SHALL show the selected step's scope, feature state, skip/fallback reason, result, and timing. Older records without audit data SHALL remain readable and SHALL be marked unavailable rather than reconstructed from evaluator names.

#### Scenario: Audited decision is selected
- **WHEN** the replay cursor is on a step associated with a recorded decision
- **THEN** the inspector displays that decision's audit and the game's effective strategy snapshot

#### Scenario: Old record has no audit
- **WHEN** a legacy JSONL record contains no decision audit
- **THEN** replay remains usable and the inspector explicitly reports that the audit was not recorded

### Requirement: CLI explain output reuses the live decision result

The tournament CLI SHALL support off, summary, and verbose explanation modes. Summary mode MUST report the effective snapshot at startup and the normalized decision path for each decision. Verbose mode MAY include a bounded set of public candidate metrics from the same evaluation. Explanation output MUST NOT trigger another evaluation or alter action selection, search budget, or transport behavior.

#### Scenario: Summary mode
- **WHEN** the tournament CLI runs with `--explain summary`
- **THEN** it prints the effective configuration once and a concise audit after each decision

#### Scenario: Verbose mode
- **WHEN** the tournament CLI runs with `--explain verbose`
- **THEN** it includes at most five already-computed public discard candidates and their available metrics

#### Scenario: Explanation disabled
- **WHEN** no explain mode is requested
- **THEN** no explanation lines are printed and recorded audit generation does not change the selected action
